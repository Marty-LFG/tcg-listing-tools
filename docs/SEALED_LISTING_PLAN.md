# Pokémon sealed listing tool — design and execution plan

Status: **proposed.** Written 2026-08-18 against `feat/invoice-requests`.
Scope: an eBay AU listing tool for Pokémon **sealed product** in English, Japanese and
Simplified Chinese, shipped from Australia.

**v1 product scope: booster packs, booster bundles, booster boxes**, factory sealed only,
listed as eBay condition **New**. Nothing else. ETBs, tins, blisters, collections, premium
collections and booster cases are explicitly out until v1 works, as are opened and damaged boxes.

**Already landed** (2026-08-18): the two sealed-valuation bugs in §7 are fixed — the eBay comps
query now carries a language token and the engine excludes our own listings. `pnpm verify` green,
477 tests.

Companion docs: `AGENTS.md` §16 (sealed valuation), §16b (stock labels), §16c (the two
listing kinds), §17 (the stock uploader), §18 (Batch Runner), §19 (the image compositor).

---

## 0. The one-paragraph version

We already have a sealed **inventory** system (`lib/sealed.mjs`, `sealed.html`) and a
complete eBay **publish** system (`lib/channels/*`, `stock-uploader.html`). They have never
been connected, and `AGENTS.md:1500` says so outright: *there is still no sealed publish
route on either channel*. The gap is not the publish plumbing, which is good. The gap is
that sealed product has **no identity** — no product catalog, no set code, no language that
anything reads, no owner-owned photos, and no postage model that survives a 1.2 kg parcel.
This plan builds identity first, then copy, then the page, then the publish path. The single
biggest finding of the survey is that the identity problem is solvable **entirely keylessly**,
including Simplified Chinese, which we had assumed was a dead end.

bytes after publish orphans every hosted image and forces a full store re-upload. Since
**zero** sealed images have ever been published, the sealed rail art is free to change right
now and expensive to change later. Do the art before the first publish, or accept it forever.

## 2. What does not exist (the actual work)

Six blockers, in dependency order. Everything else is downstream of these.

1. **No sealed product catalog.** `sealed_items.name`, `.set_name` and `.language` are
   unvalidated free text. There is no `set_code` column at all, so `findIntlSet()` always
   receives `code: undefined` and the only join to the Pokémon set universe is
   `catalog.html`'s normalised set-name string match. A listing builder has nothing to pick
   from.
2. **No owner-owned image bytes for sealed.** `listing_images.item_id` is
   `REFERENCES inventory_items(id)` with `PRAGMA foreign_keys = ON`. A sealed row cannot own
   a listing photo. Worse than a clean failure: the two tables have independent AUTOINCREMENT
   sequences, so a `sealed_items.id` that happens to also exist in `inventory_items` **passes
   the FK check** and silently attaches sealed photos to an unrelated graded card.
3. **No sealed eBay category, and no way to discover one.** Every game in
   `lib/channels/ebay-map.mjs` points at `183454` (CCG Individual Cards). A repo-wide grep
   for category ids returns only that number. The only Taxonomy calls in the codebase take a
   category id as input; there is no category-suggestion call anywhere.
4. **No `NEW` condition.** `CONDITION_ENUM` is `{ 2750: 'LIKE_NEW', 4000: 'USED_VERY_GOOD' }`
   and anything else falls back to `USED_VERY_GOOD`. A booster box published today would go
   live as *Used, Very Good* with a *Card Condition: Near Mint or Better* descriptor. Decided
   by D13 (list as **New**); still needs the three-site edit and a live check that the sealed
   category offers it.
5. **No postage model that reaches a parcel.** Bands are selected by **price alone**. The top
   band's service is `AUP_500G_SATCHEL_SIG` — a 500 g satchel at A$15.20 with nothing above
   it, which a booster box (~1.2 kg packed) exceeds. Worse in the other direction: a cheap
   sealed item resolves to band 0, an **untracked A$1.70 regular letter**, and the description
   says so out loud. Resolved by D10 — see §8.
6. **No sealed lane in the publish/reconcile/audit loop.** `runPublish`, `itemToListing`,
   `priceItem`, `reconcileListings` and the photo routes are all
   `SELECT * FROM inventory_items WHERE id = ?`.

## 3. Decisions taken

Four were answered by the owner up front; the rest follow from the survey. Anything still
open is in §12.

| # | Decision | Rationale |
|---|---|---|
| D1 | **One listing, quantity N.** Six identical boxes are one SKU on one offer at `availableQuantity: 6` | Owner's call. Also the only shape the plumbing supports well, and it avoids eBay `[25002]` duplicate-listing rejections |
| D2 | **Catalog art plus owner photos** (see §6) | Owner's call. Superseded in part by D14, which confirms permission for catalog art |
| D3 | **All three languages from day one** | Owner's call. Now cheap, because §5 found a keyless Simplified-Chinese source |
| D4 | **In-hand stock only; design for pre-orders** | Owner's call. Costs one nullable `release_date` + one `in_hand` flag now, no migration later |
| D5 | **A new standalone page, `sealed-listing-builder.html`, as an ESM module page** | See below — the highest-leverage architectural call in the plan |
| D6 | **A derived pool SKU, `BKS-PKM-EN-PAR-BOX`** | See §4 |
| D7 | **Parallel sealed listing tables, not a `kind` column on the existing four** | SQLite cannot drop the `inventory_items` FKs without a full table rebuild, and the repo's migration pattern is strictly additive |
| D8 | **Sealed is excluded from the repricer** | See §10, Phase 7 |
| D9 | **v1 is booster packs, bundles and boxes only** | Owner's call. Collapses the postage problem to **two** hand-made policies and the SKU type segment to three values |
| D10 | **Sealed postage is its own table keyed by product type, not a price band** | Owner's call that sealed shipping is flat-rate tracked and sized by product. See §8 — forcing that into the price-ordered band array is what creates a contradiction |
| D11 | **Build toward publish; copy-only is usable at the end of Phase 3** | See below |
| D12 | **The description DOES quote the postage amount, in prose and in the options table** | Owner's call, revised 2026-08-18. The condition is that it is *completely accurate and human readable*, which makes provable accuracy a design requirement rather than a nicety. See §8 |
| D13 | **Factory-sealed only, listed as eBay condition New** | Owner's call. One condition, and the builder refuses anything that is not `condition='sealed'` AND `factory_sealed=1` |
| D14 | **Catalog art may be the lead listing image** | Owner confirms permission to use catalog images for sealed product. Combined with D13 this clears both objections in §6 |

### D5 in detail: why an ESM page, not a classic-script builder

The eight existing builders are classic `<script>` pages with inline `onclick` handlers. They
cannot `import`, which is why `lib/listing-copy.mjs` exists as a **byte-identical mirror** of
each builder's inline `genTitle`/`genPitch`/`buildHTML`, pinned by
`scripts/check-listing-copy.mjs` and `test/invariants/builder-wording.test.mjs`. That mirror
is a real, permanent tax: edit one, edit all six.

`stock-uploader.html` and `stock-runner.html` are `<script type="module">` pages and can
import `lib/*.mjs` directly. Building the sealed tool that way means the sealed copy lives
**once**, in `lib/sealed-copy.mjs`, imported by the page. No mirror, no parity harness, no
tax. Given the tool also needs to publish (which no classic builder does), this is the right
side of the fork on both counts.

Precedent for the deep link: `catalog.html:430` → `pokemon-listing-builder.html?lang=&set=`
is the only stock-surface-into-builder link in the repo. `sealed.html` gains the same shape,
`?pool=<pool_sku>`. `sealed.html` stays a ledger; it does not grow listing UI.

### D11 in detail: what "publish or copy-only" means

The eight existing card builders **do not touch eBay**. They generate a title, a description and
item specifics, and stop at *Copy Title* / *Copy HTML*. You paste into eBay's own listing form by
hand. Publishing lives in a different pair of pages — `stock-uploader.html` and
`stock-runner.html` — which call the eBay API and create the listing for you.

So the question was: does the sealed tool go all the way to the API, or stop at the clipboard?

**Answer: build toward publish, but sequence it so the copy-only tool works first.** The reason
is that publishing needs three things that are unknown today — the sealed category id, its
required aspects, and the pinned parcel policies — and none of them blocks the copy path. At the
end of Phase 3 you have a working tool that writes correct titles and descriptions for a sealed
box in three languages, usable by hand while Phase 0 unblocks. Phases 6–7 then turn on the API
without rewriting anything, because an ESM page (D5) can call a publish route the moment one
exists.

## 4. The SKU scheme

**Recommended: a derived, human-readable pool SKU.**

```
sku     := "BKS" "-" game "-" lang "-" set "-" type [ "-" variant ] [ "-" cond ] [ "-" unit ]
game    := PKM | MTG | LOR | SWU | RB | OP | GEN
lang    := EN | JP | CN | TW | KO
set     := [A-Z0-9]{2,8}      ; the PRINTED set code
type    := BOX ETB BND BLI TIN COL PRC PCK CSE STD CMD PRP OTH
variant := [A-Z][A-Z0-9]{0,5} ; optional, owner-chosen from slugs already in use
cond    := OPN | DMG | NFS    ; optional, ABSENT for normal factory-sealed
unit    := "U" [0-9]{3}       ; optional, only for non-fungible units
```

Charset `[A-Z0-9-]`, uppercase only, typical length 18, hard cap 44.

**v1 uses only three `type` values — `PCK`, `BND`, `BOX` (D9).** The full map is derived from
`PRODUCT_TYPES` so the rest exist the moment scope widens, but the builder offers only those
three and refuses the others. The `variant` segment is also rarely needed in v1: boxes, bundles
and packs are seldom character-differentiated the way tins and blisters are. The exceptions to
watch are Japanese half-boxes and Pokémon Center exclusives.

Worked examples:

| SKU | Product |
|---|---|
| `BKS-PKM-EN-PAR-BOX` | English Paradox Rift booster box — one SKU, one offer, quantity 6 |
| `BKS-PKM-EN-PRE-ETB-PC` | Prismatic Evolutions ETB, Pokémon Center exclusive (GR5 in the SKU) |
| `BKS-PKM-EN-PAR-BLI-CHKLN` | Checklane blister, distinct from the 3-pack blister |
| `BKS-PKM-JP-M5-BOX` | Japanese Abyss Eye booster box (17 chars) |
| `BKS-PKM-CN-CSV95C-BOX` | Simplified Chinese CSV9.5C box — the dot stripped by rule, not guessed |
| `BKS-PKM-EN-PAR-CSE-U001` | One individually-tracked booster case |
| `BKS-PKM-EN-PAR-ETB-OPN` | Shrink removed. Separate pool, separate listing, separate price |

**Why derived rather than counted.** `sealed_items` rows are per-*acquisition* by design —
each carries its own `cost_cents`, `acquired_at`, `source_vendor`. A counter mints a new SKU
on every restock, which publishes a second competing listing for one pile of stock. A derived
SKU resolves to the same string on every relist and every restock, so `getOffersForSku` finds
the existing offer and `updateOffer` revises the quantity.

**Why it cannot collide with the singles shelf series.** `LABEL_RE` is
`/^([A-Z]{3})-(\d{1,3})$/`, anchored, demanding digits immediately after the hyphen.
`seqForLabel('BKS-PKM-EN-PAR-BOX')` returns `null`. So no sealed SKU can move the singles
counter or be counted by `maxLabelSeq` — which makes `labelTaken()`'s known blind spot on
`sealed_items` **unreachable** rather than merely improbable. Add the `sealed_items` check
anyway as belt and braces, since `POST /api/inventory/items` lets an operator hand-type a label.

**Where it lives.** `sealed_items.sku` is unchanged — it stays the per-acquisition internal
row id, and legacy `BK-SLD-PKM-000042` values are never renamed. The pool SKU is a new
`pool_sku` column, **deliberately not UNIQUE**: two acquisitions of one product share one
pool key and therefore one eBay offer. Once a pool SKU reaches eBay it is frozen and never
re-derived; if the row's identity later changes, warn — never rename, because eBay binds a
Custom label for life.

Rejected: riding the `AAA-001` shelf series (reverses a documented decision and burns
monotonic numbers), UPC as SKU (barcodeless products have no identity), PriceCharting ids
(binds our Custom label to a scraped third-party identifier), one SKU per physical unit (six
listings for one pile), a hash (unreadable off a box in a crate), lowercase or underscores
(the Inventory API puts the SKU in the URL path, and `sanitiseSkuToken` uppercases).

## 5. The product catalog — `data/pokemon-sealed-products.json`

This is the first build step and everything depends on it. **Verified live 2026-08-18**;
every source below is keyless.

### The two finds nobody in the repo is using

**TCGplayer's search API has a sealed facet.** Same endpoint and headers
`scripts/build-pokemon-mep.mjs` already calls:
`POST https://mp-search-api.tcgplayer.com/v1/search/request` with
`filters.term.productTypeName = ["Sealed Products"]`.

- `productLine: pokemon` → **2,897** sealed products
- `productLine: pokemon-japan` → **308** sealed products across **157** JP sets
- Each row carries `productName`, `setName`, **`setCode`** (a direct join to
  `pokemon-intl-sets.json`), `productId`, `releaseDate`, `marketPrice`, `description`
- Images at `https://tcgplayer-cdn.tcgplayer.com/product/<productId>_in_1000x1000.jpg` (200, ~110 KB)
- The `setName` field alone fills a large share of the 152/269 missing `name_en` values in the JP bake
- **No Chinese product line exists** — the full 67-line `productLineName` aggregation has
  `Pokemon` and `Pokemon Japan` and nothing else. TCGplayer is definitively a dead end for CN

> **Trap:** `scripts/build-pokemon-mep.mjs` filters with `if (p.sealed) continue`. Measured:
> genuine `productTypeName: "Sealed Products"` rows carry `sealed: false`. `p.sealed` is not
> the sealed flag. Copying that line into a new bake silently includes or excludes the wrong
> rows.

**wiki.52poke.com has a working keyless MediaWiki API, and it solves Simplified Chinese.**
`robots.txt` permits `/api.php`. One call —
`action=query&list=embeddedin&eititle=Template:TCG版本信息框/ZH&eilimit=500&einamespace=0` —
returns **264 CN/TW product pages**, complete enumeration, no scraping. `action=parse&prop=wikitext`
on a page gives a structured infobox. Real example, CN set CSV10C:

```
setname=共逐荣光   alt=CSV10C            pack=补充包
release=2026年7月16日
price=5张装：10（人民币元）/ 20张装：50（人民币元）      <- MSRP
packnumber=5张装：15 / 20张装：6                        <- packs per box
setlogo / packlogo / packlogobig / poster               <- box art filenames
official=https://www.pokemon.cn/tcg/product/...         <- the authoritative CN page
ja={{TCG|对战搭档}}                                      <- cross-ref to the JP set
```

Image filenames resolve via `prop=imageinfo` to `media.52poke.com` (verified 200,
image/jpeg, 90 KB at 1000×667). The same mechanism covers Japanese:
`Template:TCG版本信息框/JP` → **365 pages**.

Caveats: CirrusSearch is off so `insource:` regex search is unavailable — enumerate via
`embeddedin`, not search. The `/ZH` template mixes Simplified and Traditional; separate them
on the `alt` code prefix (`CS*` = Simplified). It is a fan wiki, so **check the licence before
redistributing any image**.

### Verified negatives, recorded so nobody re-investigates

- **TCGdex has nothing sealed.** `/v2/ja/sets/SV11B` returns exactly
  `cardCount, cards, id, legal, name, releaseDate, serie`. No `boosters` field.
- **Bulbapedia's API is Cloudflare-blocked** to a plain fetch (403, "Just a moment…").
- **pokemon-card.com's product index is a JS shell** — `/products/index.html` is 34 KB of
  nothing; `/products/ajax/getProducts.php` and `/api/products` both 404. But the *per-set*
  page **is** server-rendered: `/ex/m5/` → 45,628 B, title
  「ポケモンカードゲーム MEGA 拡張パック「アビスアイ」」, release date 2026年5月22日, hero art.
  Drive it from the set codes already in the intl bake.
- **eBay Browse/Catalog is not an identity source.** It returns seller-written listing titles,
  and every figure is an asking price (Marketplace Insights is entitlement-gated, chased and
  refused twice).

### PriceCharting, re-verified rather than assumed

`parseSealedConsole` works correctly. Measured against live HTML:

- `pokemon-pitch-black` (EN): page 1 = exactly 150 rows, **0 sealed**; page 2 = 66 rows,
  **14 sealed** (Booster Box, ETB, Pokémon Center ETB, Build & Battle Box, Half Booster Box,
  Booster Bundle, 3-Pack Blister, Single Pack Blister, four Premium Checklane Blisters, …)
- `pokemon-japanese-abyss-eye` (JA): **2 sealed** — Booster Pack, Booster Box. Same for other JP sets
- `pokemon-chinese-m3` (ZH-CN): **2 sealed**. `pokemon-chinese-sv11b`: **0**

The 150-row page-1 cap is confirmed, and sealed rows sort **after** all cards
(`sort=model-number`). So on any set with >150 cards, page 1 contains zero sealed rows —
a hand-rolled single-page fetch returns nothing for every large EN set. `walkConsolePages`
handles this correctly; use it. Note `data/pc-cache/` holds 23 card console files and **zero**
sealed ones: this path has never executed on any machine.

### Layers, in precedence order

**English** — solved, cheapest, build first.
L1 TCGplayer `pokemon` (2,897) · L2 PriceCharting `enumerateSealedConsole(pcSlug)` for the
price ladder and a second image · L3 UPCItemDB name-search for the UPC and the pack count
regexed out of the retail title.

**Japanese** — assemble from three; none is sufficient alone.
L1 TCGplayer `pokemon-japan` (308 / 157 sets) — the only source of romanised English names
with a machine-joinable `setCode` · L2 52poke `/JP` (365 pages) — native names, plus the
product types the others omit (starter decks, premium trainer boxes, gift sets) · L3
`pokemon-card.com/ex/<code>/` — authoritative native name, official release date, official
hero art · L4 PriceCharting per `pcSlug` — price ladder, but only ever 2 SKUs per set · L5
UPCItemDB name-search — JANs, verified working on a set released three months ago

**Simplified Chinese** — a single-source lane, and say so plainly.
L1 52poke MediaWiki (264 pages in one call; native name, code, type, release date, CNY MSRP,

has no product index so it cannot be enumerated independently) · L3 English name: **there is
no commercial romanisation for CN**. Fall back to the intl bake's `enEquivalent.name`, or
require an operator-entered name. Do not invent one — `setNameIsCodeOnly` exists to tell the
operator the honest answer, and GR4 forbids the guess.

Accept the CN product model on its own terms: 5张装补充包 and 20张装卡盒, not a 30-pack
booster box. Store the CN wording as a display label in the catalog rather than growing
`PRODUCT_TYPES`.

## 6. Images

**Catalog art may be the lead image (D14). Owner photos are still preferred where they exist.**

The plan originally argued the other way. Two objections drove that, and both are now closed:

1. **Licensing.** Every candidate image is third-party bytes — PriceCharting's
   `storage.googleapis.com`, TCGplayer's CDN, UPCItemDB retailer photos, `media.52poke.com`.
   **Owner confirms permission to use catalog images for sealed product** (D14), so this is
   settled and the plan takes it as given.
2. **eBay's stock-photo rule.** This bites *used* items, which is why `refuseRow` makes
   `sub_nm_no_photos` and `graded_no_photos` non-releasable. v1 lists factory-sealed stock as
   condition **New** (D13), so it does not apply. What keeps that true is the gate below, not
   good intentions.

**The gate, concretely.** The sealed branch of `refuseRow` is a scope guard, not a photo rule:

- `condition = 'sealed'` **and** `factory_sealed = 1` → releasable on catalog art alone.
- anything else → **non-releasable**, `sealed_not_new`. An opened or damaged box is out of v1
  scope and deserves a hand-made listing.

That gate is load-bearing. The moment scope widens past New, the stock-photo rule comes back
and owner photos become mandatory again, so the refusal must land before the scope does.

**Owner photos are still worth taking on the expensive stock.** A A$400–900 box sells on its
corners and its shrink wrap, and catalog art shows a pristine specimen that is not the one in
the parcel. The recommendation is catalog art as the fast path for everything, with owner
photos leading on boxes and cases where the actual condition is part of the sale. Nothing in
the build depends on this, so it stays a preference rather than a rule.

**One thing D14 does not change:** the compositor's `sub_nm_no_photos` comment about branded
rails still stands for the *singles* path. Framing catalog art in store chrome changes how a
thumbnail looks and nothing about what it is. Sealed is fine because of permission and
condition, not because the rails launder anything.

**Storage.** New `sealed_pool_images` table keyed on `pool_sku` (not on a row id), because
photos belong to the product, not to an acquisition. Mirrors `listing_images`' shape —
`position`, `kind ('owner'|'catalog')`, `local_path`, `ebay_url`, `sha256` — but is a parallel
table, per D7. Owner photos are branded at **upload**, not at publish, matching
`POST /api/listings/photos`, and the original is retained at `data/photo-originals/<sha256>.<ext>`.

**Rails.** Three jobs, all before the first publish:

1. Replace the `rails/sealed/` placeholder with real art.
2. Decide the language question. `resolveVariant` checks `productType === 'sealed'` **before**
   `language === 'japanese'`, so an English, a Japanese and a Simplified-Chinese box all get
   the identical blue rails, separated only by a text marker — and `langMarker` renders both
   CN and TW as `(ZH)` even though GR5 says they are different products. Either add
   `sealed-jp` / `sealed-cn` to the frozen `VARIANTS` array, or accept one sealed look and
   carry language in the marker only. Recommend the former, given D3.
3. Guarantee the catalog supplies a **Latin** product name for every language.
   `isRailDrawable` silently drops any CJK line rather than gambling, because Pango
   substitutes a system font on a missing glyph — Japanese renders perfectly on the Windows
   dev box and as blank boxes on ALCSERVER.

Also note `aspectReview()` measures every source against the card ratio 63/88 = 0.7159 and
flags anything below 0.95. A tall booster box at aspect 0.5 flags `aspect-far-from-card` at
30.2% off. That is a warning, not an error, and it fires on every sealed photo — decide
whether to suppress it for `productType === 'sealed'` or live with the noise.

## 7. Pricing

Sealed already has a valuation engine and it is the *right shape*: `sealedEbayValue` returns a
cluster **median** market value, where the singles engine returns an **undercut** of the
cheapest in-cluster listing. Median puts a box mid-market; undercut puts it at the front. For
high-ticket sealed the median is the correct default, with a manual override.

### Two valuation bugs — FIXED 2026-08-18

Both affected the **existing** nightly sealed valuation, not just the new tool, so they were
fixed ahead of the build.

- **Language.** `ebayQueryFor` built the comps query from `name + set_name` with no language
  token, and `matchesSealedType` had no language dimension, so a Japanese booster box was
  priced off English comps. Now `ebayQueryFor` appends the language word (`JP → Japanese`,
  `CN`/`TW → Chinese`, `KO → Korean`; English adds nothing, because an English listing is the
  one that names no language, and the existing word dedupe stops it being said twice). A new
  exported `matchesSealedLanguage(title, language)` gates comps symmetrically: non-English
  **requires** the language word, English **denies** any other language's word, and an unknown
  or blank language applies **no gate at all** (GR7 — a missing field must not become a
  refusal). Simplified and Traditional each require a Chinese word and deny the other's
  qualifier, which is the honest best available from a title.
- **Own listings.** `sealedEbayValue` had no `excludeSeller` parameter, so a sealed listing we
  published became a comp for itself. It now takes one and filters on it exactly as
  `lib/comps-singles.mjs` does, wired from `repricer.config.json`'s
  `exclude_seller_username` via a local `ownSeller()` in `lib/sealed.mjs` (duplicated rather
  than imported, because `lib/listings.mjs` already imports `PRODUCT_TYPES` from `sealed.mjs`
  and the cycle would cost more than three lines).

Covered by 20 new assertions in `test/unit/comps.test.mjs` and `test/unit/sealed.test.mjs`;
`pnpm verify` green at 477 tests.

**A third, related bug left alone deliberately.** `SEALED_STOP` in `lib/sealed.mjs:166` strips
the words `english` and `japanese` before matching a scanned barcode title to a PriceCharting
product, so a Japanese box can match an English console there too. That is the *barcode
resolution* path, not the valuation path, and changing it would shift existing matches for
every scanned product. Worth doing, but as its own change with its own before/after check.

Standing constraints: every comp in this app is an **asking** price, permanently, and the bias
is upward. Money is integer cents stored in the currency it was sourced in (GR3) —
PriceCharting is USD, eBay AU is AUD. eBay AU rejects sub-A$1.00 fixed price with error 25016.
The MSRP the 52poke infobox carries (CNY) and TCGplayer's `marketPrice` (USD) are useful
sanity anchors but must never be presented as authoritative (GR4).

## 8. Postage — sealed gets its own table, keyed by size

**Owner's decision (2026-08-18): flat rate tracked, chosen by product size.** That is a
different function from the singles model, and the design follows from taking it literally.

**Why sealed cannot just be more bands.** The singles model selects on **price** and
`validateBands` demands strictly increasing ceilings *and* strictly increasing costs, with the
last band at `maxCents: null`. A 500 g satchel for a booster pack costs less than the existing
A$15.20 signature band, so it cannot sit above it; putting it below would change which band a
A$150+ graded single lands in. Sealed postage is genuinely a function of size, not price, and
forcing it into a price-ordered array is what creates the contradiction.

**Recommended: `shipping.sealedBands`, a separate map keyed by `product_type`.**

- Validated on its own terms: unique ids, `costCents` a whole integer > 0, a pinned
  `policyId`, a `copy` key present in the sealed copy templates. **No ordering constraint**,
  because there is no scan.
- `offerBandFor` gains a sealed branch: look up `sealedBands[product_type]` first, and only
  fall through to the price-derived array for non-sealed rows.
- The price-derived band array is **left completely untouched**. No singles behaviour changes,
  and the delivered→list maths is never involved, so its two dead zones stay irrelevant.

> **Never iterate the delivered→list conversion.** `lib/shipping-bands.mjs:221-235` states it
> verbatim: solving `P = D − cost(band(P))` exactly has two dead zones. Sealed sidesteps this
> entirely — a direct lookup, not a scan.

**v1 needs exactly two hand-made policies**, because the three in-scope product types collapse
into two size classes:

| Product type | Typical packed weight | Rough size | Suggested policy |
|---|---|---|---|
| `booster_pack` | ~60 g | 65 × 92 × 20 mm | **Sealed small** — tracked satchel ≤ 500 g |
| `booster_bundle` | ~250–300 g | 120 × 90 × 70 mm | **Sealed small** — same policy |
| `booster_box` | ~1.0–1.3 kg | 200 × 145 × 85 mm | **Sealed box** — tracked satchel ≤ 3 kg |

A booster pack is ~20 mm thick, which is at the edge of Australia Post's large-letter
thickness limit, so it belongs in a satchel rather than the existing tracked-letter band even
though it is light.

**What we may not do.** Code never creates an eBay business policy. `ensurePolicy()` has no
create path, by design and by instruction, after the 2026-08-14 duplicate-policy incident. You
hand-make the two policies in Seller Hub and we pin the ids and verify them by cost.

### The description quotes the amount, and it has to be provably right (D12)

The singles frames put the figure in the text — verified live 2026-08-18, a band-1 listing
renders *"Postage is $8.26 anywhere in Australia, sent tracked with Australia Post so you can
follow it along."* Sealed does the same, reusing that owner-approved sentence shape. The
owner's condition is that the figure and the service name are **completely accurate and human
readable**, which turns accuracy into a build requirement instead of an assumption.

Today it is neither, and both failures have the same root cause: the description is rendered
from **config data that was captured or typed**, rather than from what eBay will actually
charge. The service label proved that in the worst way — a live listing reads
`AUP 500 G SATCHEL SIG` because `bootstrapAccount` fell back to prettifying the raw code. A
`costCents` that drifts from its policy would fail the same way, silently, and a buyer would
be quoted a price the checkout does not charge.

**So the sealed lane derives both from the pinned policy, and refuses to publish when they
disagree:**

- `fulfillmentTerms()` already returns the real per-service `costCents` off the policy row, and
  `verifyBandPolicies` already proves a band against its policy by cost. Extend that from a
  settings-page report into a **publish-time guard**: `publishListing` already refuses before
  the first API call when a band has no `policyId`, so add a refusal for a band whose
  `costCents` disagrees with the policy's last verified cost.
- The service **name** comes from a canonical code → name map, never from the code itself.
- `costCents` in the sealed band table is therefore buyer-facing and load-bearing, not
  decorative. It must mirror the policy, and the guard is what keeps that honest.

The rule that a free-postage policy is a hard error applies to the sealed lane too, for exactly
the same reason it applies to singles: every description quotes an amount.

**Edits this implies:**

- Sealed postage **copy** lives in `lib/sealed-copy.mjs`, not in `POSTAGE_COPY`. Because the
  sealed page is ESM (D5) and imports its copy directly, there is no eight-builder mirror to
  update — this is the mirror tax D5 was chosen to avoid, showing up as a saving.
- `settings.html` gets a **new** sealed-postage section keyed by product type, rather than
  making the existing `[0,1,2].map(...)` band editor dynamic. Cleaner, and it leaves the
  singles editor alone.
- `data/postsale.config.json` carries `postage.services` with exactly four codes. Both new
  service codes must be registered there too, or the packer is told the wrong thing on exactly
  the order where it matters most.

Two things to note rather than solve now: combined postage is not attached to any policy, so a
buyer ordering two sealed items pays postage twice (`checkPolicyConstraints` reports it as INFO;
the Inventory API offer has no combined-postage field, it is policy-level and manual). And
flat-rate tracked without signature is fine for a A$150–400 box, but worth revisiting if
high-value Japanese boxes or cases ever come into scope, since signature is the usual defence
against an item-not-received claim.

## 9. Schema

One new migration function, `migrateSealedListing(db)`, called from `initDb` after
`migrateSealed`. Additive only, matching the existing `addColumnIfMissing` pattern. There is
no migration framework, no version table, no numbered files — the whole schema is one `DDL`
template of `CREATE TABLE IF NOT EXISTS` exec'd on every open, followed by explicit migrate
functions.

```sql
-- additive columns
ALTER TABLE sealed_items ADD COLUMN set_code     TEXT;   -- unlocks findIntlSet, symbol, wordmark
ALTER TABLE sealed_items ADD COLUMN pool_sku     TEXT;   -- the eBay Custom label, NOT unique
ALTER TABLE sealed_items ADD COLUMN release_date TEXT;   -- D4, pre-order headroom
ALTER TABLE sealed_items ADD COLUMN in_hand      INTEGER DEFAULT 1;
CREATE INDEX IF NOT EXISTS idx_sealed_pool ON sealed_items(pool_sku);

-- new tables (parallel, per D7)
CREATE TABLE IF NOT EXISTS sealed_pools (
  pool_sku TEXT PRIMARY KEY, game TEXT NOT NULL, language TEXT NOT NULL,
  set_code TEXT, product_type TEXT NOT NULL, variant_slug TEXT,
  condition TEXT NOT NULL DEFAULT 'sealed', factory_sealed INTEGER NOT NULL DEFAULT 1,
  title_override TEXT, desc_override TEXT, store_categories TEXT, postage_band_id TEXT,
  ebay_listing_id TEXT, ebay_offer_id TEXT, channel_status TEXT /* , ... */ );
CREATE TABLE IF NOT EXISTS sealed_pool_images ( /* see §6 */ );
CREATE TABLE IF NOT EXISTS sealed_listing_pushes ( /* audit mirror of listing_pushes */ );
```

`title_override`, `desc_override` and `store_categories` are not optional extras. They exist on
`inventory_items` because `updateOffer` and `createOrReplaceInventoryItem` are **complete
replaces** — omitting them means every revise silently reverts the operator's hand edits.

Constrain `sealed_items.language` to `STOCK_LANG_CODES` (`EN JP CN TW KO`) from
`lib/pokemon-intl.mjs` — import it, do not add a fourth copy of `LANGS`. Today it is a bare
`<input value="EN">` read by nothing but a display badge, which is why an EN and a JP box are
indistinguishable to every automated path.

**Backfill by derivation, refusing rather than guessing.** Resolve `set_code` via
`findIntlSet(language, {code: null, name: set_name})`, then derive `pool_sku`. Where the set
does not resolve — likely for a fair share, since the only join today is a normalised set-name
string match — leave **both** columns NULL and have the builder demand them before publish.
That is GR7 and GR4 applied to identity instead of price.

**The `sku_counter` namespace for unit tags** is `BKSU:<pool-sku>`, which means that column
holds long variable strings rather than the short fixed tokens it holds today (`LABEL`, `STG`,
`SLD-PKM`). It is `TEXT PRIMARY KEY` so this is legal, just new.

## 10. Execution phases

### Phase 0 — Discovery and unblocking (mostly not code)

1. Run `enumerateSealedConsole` once for real, for an EN, a JP and a CN set. It has never
   executed. If PriceCharting turns out thinner than measured, the picker half of the tool
   shrinks and the plan changes.
2. **Discover the sealed eBay AU category ids live.** There is no way to do this in the repo —
   the only Taxonomy calls take a category id as input. Candidates worth checking sit under
   *Collectable Card Games & Accessories* (sealed booster packs, sealed booster boxes,
   sealed decks and kits), but **none of these is verified and none should be hardcoded from
   memory**. Confirm against the live AU category tree, then dump aspects with
   `node scripts/check-ebay-aspects.mjs --category <id>`.
3. **Read the aspect modes.** The `Game` aspect on 183454 is required *and* `FREE_TEXT`, which
   means a near-miss publishes cleanly and silently earns no facet. This has already bitten
   Lorcana and Riftbound for months. Check every sealed aspect's mode before choosing values.
4. **Owner:** hand-make the **two** flat-rate tracked policies in Seller Hub (§8 — *Sealed
   small* ≤ 500 g and *Sealed box* ≤ 3 kg) and hand over the ids.
5. **Confirm the sealed category actually offers `New`** (conditionId `1000`) and what, if any,
   condition descriptors it requires. The condition itself is decided (D13); what is unverified
   is that this category exposes it, since `CONDITION_ENUM` currently knows only `LIKE_NEW` and
   `USED_VERY_GOOD`. Adding `New` is a **three-site** change: `CONDITION_ENUM` at
   `lib/channels/ebay-inventory-api.mjs:17`, the `USED_VERY_GOOD` fallback at `:69`, and the
   condition mapping in `lib/channels/ebay-map.mjs:414,702`. Miss the third and a booster box
   still publishes as *Used, Very Good*.

**Exit criteria:** a category id, an aspect dump, two pinned policy ids, and `New` confirmed on
that category. None of this blocks Phases 1–3, which is the whole point of D11 — the copy-only
tool is finishable while Phase 0 is still open.

### Phase 1 — The product catalog bake

`scripts/build-pokemon-sealed-products.mjs` → `data/pokemon-sealed-products.json`, registered
in `BAKES`, ordered after `pokemon-intl`. Layers per §5. Prove the roster and **eyeball the JP

### Phase 3 — Copy

`lib/sealed-copy.mjs`: a sealed branch for `titleParts`, a sealed description frame, and the

Proposed title parts and priorities (mirroring the singles model — `fitTitle(parts, 80)`,
higher priority survives longer, separators baked into part text):

| Part | Prio | Note |
|---|---|---|
| product type words, e.g. `Booster Box` | 100 | The thing being sold |

**The code-only set problem is real and severe:** 152/269 JP sets, 64/65 Simplified-Chinese
sets and **98/98** Traditional-Chinese sets have no `name_en`, so `setEnglishName()` falls

`Surging Sparks` is a lost sale, but inventing a romanisation violates GR4. Recommended:
extend `data/pokemon-intl-seed.json` so an English set name is curated **once per set** and
reused by every product in it, and refuse to auto-generate a title when neither `name_en` nor
an operator-entered name exists.

**Proposed wording, for sign-off before it ships** (GR6 freezes it on arrival). The three
blocks mirror the singles shape — condition, protection, postage — and the postage line names
the service without a figure, per D12. The tracked phrasing deliberately reuses words already
owner-approved in `POSTAGE_COPY.tracked`, so the store keeps one voice:

> **Condition.** Brand new and factory sealed, never opened.
>
> **Protection.** Packed with padding so the corners and the wrap stay the way they left here.
>
> **Postage.** Postage is $X.XX anywhere in Australia, sent tracked with Australia Post so you
> can follow it along.

The postage line reuses `POSTAGE_COPY.tracked` verbatim, which is already owner-approved, and
its figure comes from the pinned policy rather than from anything typed (D12).

Every sealed listing this tool makes is New (D13), so unlike the singles frames there is no
condition ladder and no safest-default question to get wrong.

`sealed-listing-builder.html`, ESM module page, its own `--gold` accent added to DESIGN.md's

### Phase 7 — Publish and round-trip

The sealed publish route (`createOrReplaceInventoryItem` → `getOffers`/`createOffer` or
`updateOffer` → `publishOffer`), reconcile, withdraw, relist-watch (`kind='sealed'` already
exists), audit into `sealed_listing_pushes`.

Post-sale is nearly free: `buildInventoryLookup` already merges both stock tables into one
`bySku` map tagged `kind:'sealed'`, and `decrementSealedItem` already drains placements
correctly. Two changes: index `pool_sku` alongside `sku`, and pick which acquisition row to
drain when a pool spans several — **oldest `acquired_at` first**, so FIFO cost basis holds and
the P/L stays truthful.

**Repricer exclusion, in this same change (D8).** `lib/repricer-scan.mjs:154` scans every
active listing with no filter. A title like *"Pokemon … Booster Box Japanese Sealed 30 Packs"*
parses as card number `30` with `numberSafe` true and would be repriced off singles comps —
an up-only raise on a high-ticket item derived from unrelated data. Filter on the `BKS-`
prefix with a `sealed_listing` skip code.

**Surfaces that are sealed-blind and need a decision, not a silent gap:** `listings.html`,
`listing-match.html`, `orders.html` and `postsale.html` all return zero for `grep -c sealed`.
Publishing is not done when `publishOffer` returns 200 if the owner then cannot see, match or
withdraw the listing from any existing page.

### Phase 8 — Validation

`pnpm verify` must pass (`pnpm test && pnpm test:integration`). New work needed:

- a config pin if any new config file appears
- **`test/integration/sealed-publish.test.mjs`**, a sibling of `listings-publish.test.mjs` —

Testing trap from §20: do not bump the mtime of an existing `lib/*.mjs` to simulate staleness.
Every module `vite.config.js` imports is a watched config dependency, so Vite restarts the
whole dev server and any in-flight test dies on a closed socket. Write a throwaway file
nothing imports.
